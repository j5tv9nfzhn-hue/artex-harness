# S1 · 协议与 revision 地基 —— 交付与验收

阶段目标（[04-ROADMAP](../04-ROADMAP.md)）：让"一次运行"变成**可寻址、可增量拉取、可回放**
的数据结构。对应上游缺口 ④（图读非原子 + 无版本）与 P2（事件日志是资产）。

---

## 一、交付结果

### 1. `harness/protocol`（新包）

三级身份 + 事件信封，见 [protocol.go](../../harness/protocol/protocol.go)：

| 概念 | 映射 | 说明 |
|---|---|---|
| **Thread** | `{task_id, exploration_id}` | 一次任务的运行，整生命周期不变 |
| **Turn** | `{revision, kind, ref, summary}` | 一轮：`planner` 规划轮 / `work` work 轮 / `system` 干预 |
| **Item** | `kind, worker, tool, summary, detail, usage…` | 一个单位：`text` / `thinking` / `tool_use` / `tool_result` / `round` / `intercept` / `lifecycle` |

`Envelope{rev, thread, turn, item, seq}` 是线上格式。`activity.go` 提供
`KindOf()`（存储 kind → 线上 kind）与 `FromActivity()`（行 → 信封）两处唯一映射点：
新 kind 一律降级为 `text` 而不是丢弃——**丢一条记录比贴错标签更糟**。

> 为什么自造协议：与 Codex app-server 同因——审批流、流式 diff、线程持久化**不是工具调用**；
> 一个扁平 activity 行无法表达 (a) 可断点续传的定位、(b) 可确定性回放的区间、(c) 可做指纹
> 比对的轨迹。

### 2. revision 持久化

新增表与列（`db/schema.sql` 末尾，只增不改）：

| 对象 | 作用 |
|---|---|
| `tasks.revision BIGINT NOT NULL DEFAULT 0` | 任务当前版本，读一次即知是否 stale |
| `harness_revisions(task_id, revision, turn_kind, turn_ref, summary)` | Turn 边界；`UNIQUE(task_id, revision)` |
| `harness_turn_items(task_id, revision, activity_id)` | 事件↔轮次映射（**旁表**，不动 `activity` 热路径） |

`db/harness_revision.go`：
`NextRevision`（一条 `UPDATE … RETURNING` 取号，行锁保证并发唯一）、`TaskRevision`、
`ListRevisions`、`RevisionRange`、`RecordTurnItem`、`ActivityIDsForRevisions`、`TurnOfActivity`。

**为什么用旁表而不是给 `activity` 加列**：`activity` 上有 ~20 条上游查询带显式列清单，加列要
改全部；旁表只多一次插入，上游查询逐字节不变——这正是执行底座要的"最小 diff"。

### 3. 轮次接入引擎

`server/harness_turn.go`：

- `OpenTurn(t, kind, ref, summary)` — 取号 + 记为任务当前轮 + 广播轮次边界信封；
- `publishEnvelope` — 在 `emitActivity` 的**唯一发射点**给事件盖上当前 `rev`、编 `seq`、
  写 `harness_turn_items`，发到新通道；
- 接入点两处：`plannerLoop` 的轮次标记处（规划轮 = 一个 Turn）、`runIntent` 开始处
  （work 轮 = 一个 Turn）。**调用点本身没有被改写逻辑**，只是多了一行 `OpenTurn`。

旧 activity 通道原样保留 → 既有前端行为完全不变。

### 4. SSE 信封通道（只读，独立路由）

| 端点 | 作用 |
|---|---|
| `GET /api/harness/thread?task=` | thread 身份 + revision 窗口 + 当前 Turn |
| `GET /api/harness/revisions?task=&since=` | Turn 列表（客户端追平用） |
| `GET /api/harness/stream?task=&since_item=` | SSE：`event: harness`，`id:` = activity id，payload 带 `rev` |

**两个游标分工**：`id:`（activity id，稠密）用于浏览器 `Last-Event-ID` 断点续传；
`rev`（per-turn，语义）用于分组、回放与指纹。回放先订阅再补历史，与旧通道同一顺序，
避免订阅间隙丢事件。

### 5. `graph_overview` 单快照读（修 ④）

`db/readsnapshot.go`：`WithReadSnapshot(ctx, fn)` 把 store 的**读**钉到一个
`REPEATABLE READ, READ ONLY` 事务；读路径统一走 `q()`（`tx` 绑定则用 tx，否则用池）。

改造范围（读路径，写路径一律不碰）：

| 文件 | 站点数 |
|---|---|
| `db/exploration.go` | 48 |
| `db/assets.go` | 11 |
| `db/digest.go` | 8 |
| `db/task_scope.go` / `task_assets_context.go` / `asset_dsl.go` / `task_assets.go` / `constraints.go` / `exploration_sources.go` | 24 |

`AssetStore` 的读快照用**独立字段 `readTx`**，与既有写事务 `tx` 分开——绑定读快照绝不可能
把一次写折进只读事务。

`agent/tools.go`：`graphOverviewData()` 保留为无 ctx 入口；新增
`graphOverviewDataCtx(ctx)` 在快照内渲染，失败时**降级直读并打日志**（宁可给出可能撕裂的
态势，也不能让探索因读不到态势而停摆）。planner/worker 的 prompt 渲染与 `graph_overview`
工具都改用 ctx 版本。

**刻意不在快照内**：资产覆盖度（`t.as`，另一个表族，且字段本身对模型标注为"粗略估计、
仅供参考"）与跨任务黑板（`relatedTaskOverviews`，按设计就是"其他任务的活视图"）。这两处
在代码注释里写明了理由。

## 二、验收点与结果

| # | 验收点 | 方法 | 结果 |
|---|---|---|---|
| A1 | 快照不被并发写穿透 | `TestReadSnapshotIsolatesConcurrentWrites`：快照内读到 1，期间另一连接提交第二行，**同一快照再读仍为 1**，快照外读为 2 | ✅ 通过（真实 PG 16） |
| A2 | 快照只读 | `TestReadSnapshotIsReadOnly`：快照内尝试 INSERT 必须被拒 | ✅ 通过 |
| A3 | revision 并发唯一、单调 | `TestNextRevisionIsMonotonic`：25 goroutine 并发取号，无重复，`tasks.revision == 25`，边界严格递增 | ✅ 通过 |
| A4 | 事件↔轮次映射可查 | `TestTurnItemMapping`：`TurnOfActivity` / `ActivityIDsForRevisions` 正反查一致，越界查询返回空 | ✅ 通过 |
| A5 | 无 DB 时不 panic | `TestWithReadSnapshotWithoutDBEnsuresNilSafety` | ✅ 通过 |
| A6 | 协议映射与信封形状 | `go test ./harness/protocol`：kind 映射（含未知 kind 降级）、Addressing、usage 仅在终端项、legacy rev=0、JSON 键位 | ✅ 通过 |
| A7 | 不破坏上游包 | `go build ./...`；`go test ./agent/` 与上游逐条比对 FAIL 集合 | ✅ 一致（唯一失败为**上游既有** `TestGraphOverviewExpandsAssociatedCompanyScope`，在 pristine 上游同样失败，见下） |
| A8 | schema 幂等 | 测试库中新表自动创建：`harness_revisions` / `harness_turn_items` | ✅ |

**关于 A7 的既有失败**：`TestGraphOverviewExpandsAssociatedCompanyScope`
（`agent/blackboard_inheritance_test.go:87`，"task scope missing"）在**未修改的上游代码**
上同样失败，因此不是本阶段引入的回归。已如实记录，未修改该测试。
