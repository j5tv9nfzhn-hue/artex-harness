本 ADR 逐条记录业主确定的 5 项口径。**执行时不得自行改动或加固**（业主明确要求）。
需要偏离时必须回到本文件修订，并在 [PROVENANCE.md](../../PROVENANCE.md) 中登记。

## 决策 1 · 许可证继承 AGPL-3.0 + 最强免责声明

**决定**：采用方案 (A)。`artex-harness` 继承上游 ARTEX 的 **AGPL-3.0**，并附加尽可能强的
免责声明（[DISCLAIMER.md](../../DISCLAIMER.md)）。

**理由**：执行底座是复制而来的衍生作品，AGPL 的传染性使其许可不可选；且 AGPL 第 13 条
（网络服务须向使用者提供源码）与本项目"公开、可审计"的定位一致。

**后果**：

- `LICENSE` 为上游逐字节副本；
- 任何通过网络提供服务的部署，必须向使用者提供对应完整源码；
- `DISCLAIMER.md` 覆盖：授权前提、禁止用途、AS IS 无担保、责任限制与赔偿、许可证与网络义务、
  双用途与出口合规，并**诚实说明**"免责声明不能让违法使用合法化"（见该文件第七章）。

**替代方案（已否决）**：(B) 不继承 AGPL → 必须完全不复制上游代码，与决策 2 冲突；
(C) 先私有 → 业主选择公开。

## 决策 2 · 行为一致性 = 同提示词 + 同策略

**决定**：采用方案 (A)。一致性口径为**同一提示词 + 同一策略**；**验收标准仅为"拒绝话术与
行为逻辑一致"，不要求模型权重一致**。

**理由**：

1. 提示词正文（8 份种子）、内置拦截规则（20 条 deny）、阻断话术、hook 语义、压缩与终止
   参数**逐字决定**模型表现，因此"复用同源实现"是达到一致的最可靠路径；
2. 模型权重由业主后续自行配置（决策 3），无法也不应作为一致性前提；
3. 度量方法必须匹配口径 → 选用**确定性可 diff** 的指标（话术逐字、拦截命中集），
   而不是模型行为评分类指标。

**验收实现**：见 [03-ARCHITECTURE §7](../03-ARCHITECTURE.md)（双跑对照 + 行为指纹回归 +
"原本拦截→变为放行"即红线的门禁）。

**后果**：所有非必要改动被禁止——这也是本仓库阶段 0 相对上游只有 1 处代码改动
（`selfupdate` 更新源）的原因。

## 决策 3 · LLM 端点不预设供应商，沿用双格式多轮询

**决定**：采用方案 (A)。沿用上游的**双格式（Anthropic / OpenAI）+ 多配置轮询 + 熔断**
机制（`agent/provider.go`、`llmpool/`）；**不预设、不绑定任何具体供应商**。

**理由**：业主将自行配置"便宜的模型"；harness 不应把某一家的端点、模型名或默认值写进
代码或文档。

**落地约束**：

- 不新增任何 provider 默认值/config 预设；
- 不在 README 或示例中给出具体供应商的端点或模型名；
- API key 只从进程环境或 UI 配置读取（上游行为），不写入仓库（`.gitignore` 已含 `.env`
  `config.json` `jwt.key`）；
- 上游遗留的环境变量名 `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` **保留**——它们是双格式的
  格式判别入口，属机制而非"预设供应商"；如需在 UI 里配置，走上游既有路径。

**后果**：`llmpool` 的轮询链、熔断冷却、quota-aware 识别等既有能力全部可用；一致性对照
必须在**同一端点同一模型**下跑上游与本地两侧（否则比对无意义）——记在此处以备执行时遵守。

## 决策 4 · 部署：裸机优先，不做公网部署方案

**决定**：采用方案 (A)。在本机云电脑上测试；**不做公网部署那套复杂方案**；新项目同样要
支持**裸机运行**。

**理由**：定位是本机可控的 harness，不是托管服务；公网部署会引入反代/HTTPS/多租户/SSO
等与当前目标无关的复杂度。

**落地**：

- 运行形态：单二进制（`CGO_ENABLED=0`）+ PostgreSQL + 本地文件系统；
- 守护：`start.sh` / `start.bat`（换装协议依赖退出码 75 契约）；systemd 单元示例见
  [03-ARCHITECTURE §5.3](../03-ARCHITECTURE.md)；
- **不新增**：反代配置、HTTPS 证书自动化、多租户、K8s/容器编排、云托管适配。

**保留**：内嵌前端（`-tags embedui`）与 `docker-compose.yml`（上游既有，作为可选项而非主路径）。

## 决策 5 · 执行能力边界

**决定**：采用方案 (A) 的**业主修改版**——

- **保留执行能力**（不做 dry-run / 不做模拟执行）；
- **只对最极端的破坏行为做拦截**（例：删库跑路）；
- **不加入"强制硬约束"**；
- **不加入"全审批"机制**。

**完整的技术论证、残留风险与实现边界见 [ADR-0003](0003-capability-boundary.md)。**
