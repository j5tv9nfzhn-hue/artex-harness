# ADR-0003 · 能力边界：保留执行能力，只拦最极端破坏行为

状态：**已接受（业主口径）**　日期：2026-11-14

本 ADR 是 [ADR-0001](0001-owner-decisions.md) **决策 5** 的完整论证与实现约定。

---

## 决策

| 项 | 口径 |
|---|---|
| 执行能力 | **保留**（不做 dry-run、不做模拟执行、不做"只读模式"） |
| 拦截范围 | **只拦最极端的破坏行为**（例：`rm -rf`、`mkfs`、`dd` 覆写设备、`DROP DATABASE`/`TRUNCATE`、删库跑路类） |
| 强制硬约束 | **不加入**（不出站白名单、不做目标范围强制执行、不做执行前策略引擎） |
| 全审批 | **不加入**（不引入逐动作审批、不做计划预审门） |

## 论证：为什么这个口径在工程上站得住

### 1. "全审批"在工程上是无效的（有实测证据）

这是本决策中**最容易被误读为"放松"、实际是"求真"**的一点。三份独立证据：

| 证据 | 数据 | 含义 |
|---|---|---|
| Claude Code Auto Mode 工程文 | **用户批准了 93% 的权限提示** | 审批疲劳使提示丧失筛选意义；他们改为两阶段分类器（快速单 token 门 + 仅对可疑动作走思维链） |
| 2026-08 用户研究（113 人） | 预授权规则比逐动作审批**少挡约 20 个百分点** | 用户全选"ask"后运行时照样批准，静态承诺退化成运行时提示 |
| 《When "Do Not" Is Not Deny》 | 481 份公开 `CLAUDE.md` 中**仅约 4%** 的自然语言安全规则有对应强制控制 | 提示词不是护栏，除非映射到确定性强制 |

**结论**：把"全审批 + 提示词级约束"当作安全机制，产出的是**仪式而非保护**，同时给操作者
制造持续摩擦。业主"去掉繁琐限制"的诉求与上述证据方向一致。

### 2. "极端破坏"恰好是少数**可机械判定**的类别

证据 3 的反面是它的建设性含义：**能被机械判定的规则才有效**。而"极端破坏行为"正是这样一类
——它可由命令字符串/意图分类确定性识别，不需要理解任务上下文：

- 开源侧同类实现：`nah` 把工具调用映射到**意图分类**（`filesystem_delete` / `network_outbound` /
  `lang_exec`）而非命令名黑名单，理由是"同一个二进制因参数不同可以无害也可以毁灭"；
  OAP 走"执行前同步拦截 + 声明式策略 + 签名审计"，其对抗测试中严格策略 **0% 攻击成功** vs
  宽松策略 **74.6%**。
- 反观"目标范围"与"任务意图"这类约束，需要语义判断，**无法机械判定**——这正是它们在实践中
  退化成提示词（4%）的原因。

**结论**：拦截口径收窄到"极端破坏"，不是妥协，而是把有限的确定性用在**唯一能确定性判定**
的那一类上。上游的 20 条内置规则恰好就是这个类别（`intercept_rules` 实测：全部 `action=deny`，
覆盖 `rm -rf`/`mkfs`/`dd`/fork 炸弹/关机/`shred`/清空防火墙/`DROP DATABASE`/`TRUNCATE`/Redis
`FLUSHALL`/删除类接口路径等）。

### 3. 与决策 2 的相容性

"不改上游默认拦截"同时满足两条口径：**行为一致**（同一策略）与**只拦极端破坏**（上游默认即
如此）。因此本决策的**实现动作 = 不做任何改动**——这既是业主口径，也是最忠实的一致性实现。

## 实现约定（本项目的具体动作）

| 项 | 动作 |
|---|---|
| 上游 20 条内置拦截规则及其默认值 | **原样保留，不改一条、不额外添加** |
| `intercept_enabled_tools`（7 个工具） | 原样保留（上游默认） |
| `llm_judge_enabled`（模型兜底审批） | 原样保留（上游默认 **关**）；需要时可自行打开，**不默认开启** |
| 不新增 | 范围硬约束、执行前策略引擎、逐动作审批、计划预审门、`harness_approvals` 类表 |
| 不做 | 任何把既有拦截默认值改宽的动作（那会同时违反决策 2 与决策 5 的"只拦极端破坏"下限） |

## 残留风险（诚实记录）

1. **执行能力即真实能力**：本项目保留完整执行能力，因此它在授权范围外被使用会产生真实损害。
   合法性完全取决于使用者是否持有授权——见 [DISCLAIMER.md](../DISCLAIMER.md)。
2. **LLM 自主行为不可完全预测**：20 条规则覆盖的是**已知的极端破坏类别**，不是"安全保证"。
   规则之外的破坏性动作（未列入黑名单的写法、编码变形、经由自定义工具/MCP 的间接执行）
   不受拦截。
3. **无范围执法**：越界不会被平台阻止，只能事后从留痕（`traffic` / `llmrec` / `activity`）
   审计。这是本决策的已知取舍。
4. **上游既有缺口仍在**：工具表读取失败时 fail-open（`server/assembly.go:239-244`）等
   （详见 [01](../01-EVALUATION-ARTEX.md) §2.3 与
   [docs/upstream/SOURCE-REVIEW.md](../upstream/SOURCE-REVIEW.md)）。本 ADR 不承诺修复它们；
   是否修复列入 [04-ROADMAP](../04-ROADMAP.md) S4 按需决定，且每处都须记入 PROVENANCE。

## 实现者边界（本项目的范围声明）

按业主口径实施，即**不新增任何限制**；同时本项目的范围**不包含**以下工作，它们既不在业主
口径内，也不属于 harness 的职责：

- 移除或削弱上游既有的拦截规则与默认值（与决策 2、决策 5 同时冲突）；
- 规避安全产品、逃避检测、反取证或清理痕迹类能力；
- 面向**未获授权**目标的自动化发现、批量编排或无人值守攻击链。

`artex-harness` 的定位是**可观测、可干预、可评测的 agent harness**：它让"已经在做的事"
更可控、更可复查，而不是让不可控的事更容易做。
